# AI Concentrate：マーケティング制作で世界トップになるための実装計画

作成日：2026-10-07 ／ 対象ブランチ：`codex/scalable-studio`
前提：ユーザー承認済みの順序 **プロトタイプ → AI生成・編集の実稼働 → 動画制作** を変えない。
現在のマイルストーンはプロトタイプ。この文書は計画であり、ここに書いた未実装機能を「提供中」と表現しない。

---

## 0. 結論（1ページ要約）

- **勝ち筋**：「AIが書く」ではなく、**根拠つき・ブランド準拠・人間承認つきの変更提案**を、Web／MCP／CLIの
  どこからでも同じ操作で扱えるようにする。競合の多くは「生成して終わり」で、出典確認・差分レビュー・
  エージェントの権限管理が弱い。ここで勝つ。
- **North Star 指標**：*承認された提案の数（週次）× 承認時の無修正率*。
  「速く書ける」ではなく「そのまま出せる品質で、安全に、何度も回せる」ことを測る。
- **今回（2026-10-07）実装した範囲**：フェーズ1のうちフロントエンドの土台。AIポリシーとブランドプロフィールの
  編集、利用量と予算の表示、資料の管理（AI除外・削除・続きの読み込み・抜粋検索・機微情報の警告）、
  提案レビューの刷新（差分、出所、事実警告、却下、履歴）、企画とワークスペースの削除。
  詳細は §6 の進捗表。
- **次の90日**：フェーズ2（AI生成の実稼働）の完了条件を満たす。具体的には、本番プロバイダでの eval 合格、
  非同期ジョブ、LLM審査、編集率フィードバック、可観測性。

## 1. 世界トップの定義（何で一番になるか）

| 軸 | 世界トップの状態 | 測り方 | 現状 |
|---|---|---|---|
| 品質 | 承認時の無修正率 ≥ 60%、事実警告の見逃し 0 | 編集率（Levenshtein比）、eval の事実チェック再現率 | 編集率は未計測。eval は固定7ケース |
| 信頼 | 出典のない数値・固有名詞を自動で検出。ブランド禁止表現 0 件で出荷 | `warnings` 発火率、禁止表現の eval | 警告の生成と表示は済み。禁止表現は profile 経由で投入 |
| 速度 | 提案の p50 が 8秒以内、p95 が 25秒以内。編集・保存は p95 300ms以内 | `ai_runs.latency_ms`、Web Vitals | 計測列はあるが、ダッシュボードはない |
| コスト | 承認1件あたりの AI 原価 ≤ ¥5。キャッシュヒット率 ≥ 70% | `ai_runs.cost_micros`、`cached_input_tokens` | 記録済み。目標値の監視はない |
| エージェント対応 | MCP クライアント3種（Claude, ChatGPT, Cursor）で同じ操作が通る。誤適用 0 | MCP の契約テスト、audit | サーバー側は対応済み。実クライアントでの検証は未実施 |
| プライバシー | 送信前マスク、資料単位のAI除外、削除の伝播 ≤ 30日、監査ログ | 保持ジョブのログ、audit | 実装済み（デプロイ後の検証が残る） |
| 体験 | 最初の承認まで ≤ 10分（オンボーディングから） | Time-to-first-approval | 未計測 |

競合との差（調査メモ）：Jasper／Copy.ai／Writer はブランドボイスとテンプレートが強い。
一方で、ソースへの根拠づけ、差分レビュー、外部エージェントへの安全な権限委譲は弱いか存在しない。
Clueso と Okara は「制作フロー」の分かりやすさが強み。参考：`design/ux-v3/CLUESO-RESEARCH.md`、
`docs/marketing-agent-quality.md`。

## 2. 設計原則（判断に迷ったらここに戻る）

1. **提案が先、適用は人間**。AIの出力は常に `changes` に入れる。自動適用はワークスペースのポリシーで明示的に許可した場合だけ。
2. **すべての能力は1つの Operation**。Web／REST／MCP／CLI の挙動差をつくらない（`lib/domain/operations.ts`）。
3. **ワークスペースの規模に比例するレスポンスを作らない**。一覧は要約とカーソル、本文は1件ずつ取得する。
4. **原価は設計で下げる**。キャッシュしやすいプロンプトの並び順、関連度で絞った文脈、差分出力、tier ルーティング。
5. **嘘をつかない UI**。未接続の機能は未接続と表示する。サンプルや書き出しを「生成」と呼ばない。
6. **測れないものは出さない**。新しい AI タスクは eval と `ai_runs` の記録をセットで出す。

## 3. フェーズ計画

### フェーズ1：プロトタイプの完成度を上げる（現在。〜2026-10末）

目的：バックエンドの能力をすべて UI から安全に使えるようにし、デザインと実装の差を埋める。

| # | 項目 | 完了条件 | 状態 |
|---|---|---|---|
| 1-1 | 型付き Operation クライアント（`operation(name, args)`） | 新しい UI 呼び出しが型チェックされ、エラーが表示言語に合わせて表示される | ✅ |
| 1-2 | 設定：AI ポリシー（送信可否、エージェントの適用権限、許可プロバイダ） | オーナーだけが編集できる。リビジョンが衝突したら再読み込みを促す | ✅ |
| 1-3 | 設定：ブランドプロフィール（ボイス、用語集、禁止表現） | 編集者以上が保存でき、AI のコンテキストに入る | ✅ |
| 1-4 | 利用量と予算の表示 | 今月の実行回数、トークン、キャッシュ率、原価、自分の残予算を表示 | ✅ |
| 1-5 | 資料の管理 | AI除外の切り替え、削除の確認、ページング、本文の続きを読む、抜粋検索、機微情報の警告 | ✅ |
| 1-6 | 提案レビューの刷新 | 単語単位の差分、出所（サーバーAI か外部エージェントか、モデル名）、事実警告、却下、状態別の履歴 | ✅ |
| 1-7 | 企画の削除・ワークスペースの削除 | 確認ダイアログを通す。ワークスペースは名前の入力が必要で、30日の猶予を明示 | ✅ |
| 1-8 | Figma の実装同期 | 実装画面ごとに編集可能なフレームを用意し、台帳とハッシュを更新 | ⛔ Figma コネクタが未認可で止まっている（§7） |
| 1-9 | モバイル／英語の画面パリティ | 390px と EN で主要な9ビューが横スクロールなしで表示される | △ 今回の追加画面はブラウザで検証済み |
| 1-10 | エージェント接続の一覧と失効 UI | `agent_connections` のテーブル、一覧、失効の操作 | — 次の作業 |

### フェーズ2：AI生成・編集の実稼働（2026-11〜12）

目的：本番プロバイダで「そのまま出せる提案」を安定して出す。

| # | 項目 | 設計メモ | 完了条件 |
|---|---|---|---|
| 2-1 | 本番プロバイダの接続と eval の合格 | OpenAI と Claude の両方で `npm run eval` を実行。tier ごとにモデルを決める | 固定 eval で合格率 ≥ 95%、事実警告の再現率 100% |
| 2-2 | 非同期ジョブ（`jobs` テーブルと Queue／Cron の実行器） | Vercel は Queue、Sites は Cron にフォールバック。`production_revise` は jobId を返し、Web はポーリング | 50秒の締め切りに依存しない。再試行は冪等 |
| 2-3 | 新しい AI タスク | `channel.derive`（原稿→X/記事/Reddit）、`brief.extract`（資料→ブリーフ）、`claims.check`、`source.summarize` | タスクごとに eval 10件以上、`version` の管理 |
| 2-4 | LLM 審査（二次チェック） | fast tier で、主張と出典の対応、禁止表現、トーンを審査し、`warnings` に追記 | 誤警告率 ≤ 10% |
| 2-5 | 編集率のフィードバック | 適用後に人が書き換えた量を `ai_runs` に結びつけて記録 → 週次レポート | North Star を計測できる状態 |
| 2-6 | 可観測性 | OTel のトレース（operation → router → provider）、レイテンシと原価の SLO アラート | p95 と原価のダッシュボード |
| 2-7 | 汎用レート制限 | ユーザー単位と接続単位のトークンバケット（D1/libSQL で原子的に） | 429 に Retry-After を付ける |
| 2-8 | アイテムの正規化、content-addressed な revisions | `items` テーブルと、本文ハッシュで重複を排除した `blobs` | 1企画あたりの保存量 -70% |
| 2-9 | ストリーミング表示 | SSE で提案の生成途中を表示（適用はできない） | 体感の待ち時間が半減 |
| 2-10 | MCP の outputSchema と resources | 実クライアント3種で契約テスト | すべてのツールが構造化出力を返す |

### フェーズ3：チームと商用化（2027-01〜02）

招待とロール管理、課金（Stripe。使用量は `ai_runs` から集計）、SSO、監査ログの閲覧 UI、
データ所在（リージョン）の選択、プライバシーポリシーと DPA、SOC2 準備（変更管理、アクセスレビュー）。

### フェーズ4：配信と効果測定（2027-02〜03）

X／YouTube／ブログの下書き投稿（OAuth、人の承認は必須）、UTM の自動付与、実績の取り込み、
仮説と実績を突き合わせ、次の企画を提案するループ（ここで North Star を「承認数」から「成果につながった承認数」に拡張する）。

### フェーズ5：動画制作（2027-03〜）

承認された台本 → 絵コンテ → 音声 → レンダリング。いずれも人間のレビューを挟んでから公開する。
ジョブ基盤（2-2）と素材ストレージ（R2/Blob）を前提にする。

## 5. コストモデル（承認1件あたり）

- 入力：プロフィールと関連チャンクで ≤ 6k tokens（キャッシュヒット時は 1/10 の料金）、タスク部分 ≤ 1k
- 出力：差分モードで平均 400 tokens
- 目標：standard tier で 1提案あたり約 ¥1.5、承認率 50% なら承認1件あたり ¥3 以下
- 主なレバー：キャッシュ順の維持（`system → context → task`）、tier ルーティング、LLM 審査は fast tier だけ、
  却下された提案の傾向をプロフィールへ反映して試行回数を減らす

## 7. リスクとブロッカー

| リスク | 影響 | 対策 |
|---|---|---|
| Figma コネクタが未認可 | AGENTS.md の同期ルールを満たせない | 台帳に `blocked` として記録。認可されたら、記録してある画面一覧を同期する |
| 本番プロバイダでの品質が不明 | フェーズ2の完了条件 | eval を拡充してから、本番キーで実行する |
| 50秒の締め切り（Vercel） | 長文の改稿が失敗する | 2-2 のジョブ化 |
| D1 の書き込み競合 | 同時編集で保存が衝突する | CAS は実装済み。item_patch の普及で衝突範囲を小さくする |
| 単一オーナー前提の UI | チーム利用 | フェーズ3 |
